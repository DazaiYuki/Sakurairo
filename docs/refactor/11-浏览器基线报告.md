# 11 · 浏览器基线报告（修正版）

> 背景：2026-09-24 评估 T4（polyfill.js）时，本工具基于"内容特征"推断
> polyfill.js 是死代码并移除其加载，导致首页全屏 canvas 消失、高度塌缩 1014px。
> 主题核心作者指出：**浏览器基线都没搞清楚就乱提建议**。批评成立。
> 本文档是补课：把基线与构建管线一次查清，作为后续所有 JS 相关决策的前提。

---

## 一、官方浏览器基线（查证于源码仓库）

主题 JS 源码在外部仓库 `Fuukei/Sakurairo_Scripts`（见文档 01 的硬约束），
其 `package.json` 声明：

```json
"browserslist": [
  "last 20 Chrome versions, last 6 Safari versions, last 10 Firefox versions"
]
```

以 2026-09 的版本号折算，大致相当于：

| 浏览器 | 基线 | 意味着 |
| --- | --- | --- |
| Chrome | 最近 20 个大版本（约 Chrome 120+） | ES2022 语法与 API 全面可用 |
| Safari | 最近 6 个大版本（约 Safari 16+） | 同上 |
| Firefox | 最近 10 个大版本（约 Firefox 128+） | 同上 |

**结论：官方支持目标是非常现代的浏览器。** 不支持 IE11、不支持 ES2020 之前的
语法环境。`app.js` 里的 `?.` 与 `??`（ES2020）未被转译即为佐证——browserslist
判定目标环境原生支持。

## 二、构建管线（webpack.common.js 关键配置）

```js
// babel：按需注入 polyfill
['@babel/preset-env', { useBuiltIns: 'usage', corejs: '3.46' }]

// webpack：把 node_modules 里的运行时依赖拆成名为 polyfill 的初始 chunk
splitChunks: {
    cacheGroups: {
        polyfill: {
            test: /[\\/]node_modules[\\/](@babel|core-js|regenerator-runtime)[\\/]/,
            name: 'polyfill',
            chunks: 'initial',
            priority: 60,
            enforce: true,
        },
    },
}

// webpack 自身也以 browserslist 为目标
target: 'browserslist'
```

由此得出 polyfill.js 的**真实身份**：

1. babel `useBuiltIns: 'usage'` 会把源码用到的标准 API 重写为 core-js 导入，
   并注入 @babel helpers；
2. webpack 把这些来自 `@babel` / `core-js` / `regenerator-runtime` 的模块
   **刻意拆分为名为 `polyfill` 的初始 chunk**（上述 cacheGroup，`enforce: true`）；
3. **app.js 的转译代码直接依赖这个 chunk 里的模块**（模块 ID 级别的 require）。

即：**polyfill.js 不是"给老浏览器的可选补丁"，而是 app.js 的运行时模块来源**，
两者是同一构建管线的配套产物，服务同一个（现代的）浏览器基线。

## 三、为什么"现代浏览器不需要 polyfill"的推理是错的

错误推理链（已废弃）：

```
polyfill.js 内容全是 ES6 API 补丁
→ app.js 用 ES2020 语法，老浏览器跑不了 app.js
→ 需要 ES6 补丁的浏览器不存在
→ polyfill.js 是死代码
```

每一步"看似"都对，**但整体建立在"polyfill.js 的用途是给老浏览器补 API"这个
未经查证的前提上**。真实情况：

- `useBuiltIns: 'usage'` 的注入对象是**当前源码**用到的 API，与"老浏览器"
  无关——即使目标全是最新的 Chrome，源码用到的某些 API 仍会走 core-js
  （实现不一致、超出内置范围、或干脆是 babel helper 的重定向）；
- 箭头函数出现在 polyfill.js 里**恰恰是基线现代的证据**（babel 输出允许
  使用 browserslist 支持的语法），当时却被误读为"自相矛盾"；
- 移除它 = 破坏 webpack 模块图 = app.js 相关功能静默失败——实测证实
  （首页 900px 全屏 canvas 消失，console 无报错，见文档 04 第十节）。

## 四、基线对后续决策的影响

| 决策 | 基线带来的结论 |
| --- | --- |
| polyfill.js（T4） | **不可移除**（已实测，见上） |
| `js/*.map`（T7） | `devtool: 'source-map'` 是构建配置；清理需改源码仓库配置，主题仓库删了会被 CI 加回。且 `.map` 不影响线上性能（仅 devtools 按需加载） |
| 未来任何 JS 优化 | **必须在 `Fuukei/Sakurairo_Scripts` 里做**，主题仓库只消费产物 |
| WP `wp_enqueue_script` 依赖链 | `app → polyfills`、`page → app → polyfills` 是构建产物关系的镜像，不得拆改 |

## 五、方法论修正（写给后续的自己）

1. **查基线的正确顺序**：源码仓库 `browserslist` → babel/webpack 配置 →
   产物内容特征。**产物特征只能用来验证假设，不能用来建立假设。**
2. **对构建产物，"它看起来像什么"没有意义**，"构建配置说它是什么"才有一意义。
3. **任何对产物的增删，先跑视觉回归**——安全网存在的意义就是拦截这类
   "推理正确但前提错误"的改动。本次事件中它工作了，这是它第二次
   抓住静默失败（第一次见文档 04 第九节 prev/next 卡片案例）。
