# 07 · T2「恢复区块样式按需加载」视觉影响评估

> 评估日期：2026-09-24
> 评估对象：`functions.php` 中关闭「区块资源按需加载」的 4 个 filter + 强制 enqueue 的 4 个区块样式表
> 方法：本地环境（WordPress 7.1.2 / PHP 8.3.35）临时移除该逻辑 → 采集 28 张全页截图 → 与改动前逐像素对比 → 回退
> 结论：**体积收益真实（−137.5 KB / −38%），但会造成视觉变更，且根因比预期严重**

---

## 一、为什么做这个评估

文档 02 把 T2 列为「主题侧最大的单项体积收益」：线上合并包内含 **1851 条 `wp-block-*` 规则**，
而每个页面都被强制全量加载整个区块样式库。

但「省体积」和「外观不变」在这里天然冲突 —— 区块样式参与正文渲染。
所以在决定是否推进之前，必须先把「变化到底有多大」量出来。

---

## 二、体积收益（实测，首页）

| | 样式表数 | 传输 | 原始 |
| --- | --- | --- | --- |
| 改动前 | 4 | 310.1 K | 362.1 K |
| 改动后 | 3 | 172.6 K | 224.6 K |
| **节省** | −1 | **−137.5 K** | **−137.5 K（−38%）** |

省掉的正是整个区块样式库 `wp-includes/css/dist/block-library/style.min.css`。

> 注：本地 PHP 内置服务器**不做 gzip**（传输量 = 原始量），所以「传输」列偏高。
> 生产环境经 gzip 后实际约省 20~25 KB。原始体积的对比仍然有效。

---

## 三、视觉影响

### 3.1 总体：28 张里 8 张有变化，全部是文章页

```
共 28 张：一致 20，尺寸变化 8，其他 0
```

| 页面 | 是否受影响 |
| --- | --- |
| 首页 `01-home` | ✅ 零变化（0 像素） |
| **文章页 `02-post`** | ❌ 有变化 |
| **代码长文页 `03-post-code`** | ❌ 有变化 |
| 独立页面 `04-page` | ✅ 零变化 |
| 搜索结果 `05-search` | ✅ 零变化 |
| 404 `06-404` | ✅ 零变化 |
| 搜索无结果 `07-search-empty` | ✅ 零变化 |

**首页、独立页、搜索页、404 页完全不受影响** —— 受影响的是**正文里的区块元素渲染**。
文章页与代码长文页各 4 种组合（2 视口 × 2 配色）全中，说明与配色、视口无关，是内容层面的变化。

### 3.2 变化性质：先区分「位移」与「真实重排」

页面高度变了，`compare.js` 只能报「尺寸变化」，无法说明变化有多大。
为此新增 `align.js`（逐行垂直对齐检测）和 `shiftcmp.js`（位移补偿后逐像素对比）：

| 截图 | 高度变化 | ① 直接对比 | ② 位移补偿后 | 减少 |
| --- | --- | --- | --- | --- |
| 文章页 · 桌面 | **−12px** | 1.397% | 0.245% | **82.4%** |
| 文章页 · 移动 | **−24px** | 3.829% | 0.965% | 74.8% |
| 代码长文页 · 桌面 | **+2px** | 1.118% | 0.655% | 41.4% |
| 代码长文页 · 移动 | **+4px** | 2.309% | — | — |

**文章页：变化主体是位移。** 补偿后差异减少 82%，说明绝大部分差异只是内容整体上下移动，
文字、字号、行内样式都没有改变。移动端位移是桌面的两倍（−24px vs −12px），
因为窄屏换行更多，同一个高度差异被放大。

**代码长文页：位移不是主因。** 只减少 41%（且高度仅差 2px），
残余差异来自 2px 非整数倍偏移造成的抗锯齿边缘不匹配，以及少量的样式差异。

### 3.3 唯一的实质样式变化：引用块左侧竖线消失

对文章页做位移补偿后，残余差异收敛到**一处 13 行高的区域**（y858~870），裁图确认：

```
改动前（左）：引用块左侧有一条竖线，竖线内缩进排版
改动后（右）：竖线消失，引用文字直接顶到左边
```

即 **`wp-block-quote` 的左侧边框（`border-left`）丢失**。

代码长文页的残余差异集中在代码块、列表区域（y594~1223，占页面 21%~43%），性质类似。

## 四、根因：按需加载在 Sakurairo 上**几乎失效**

这一条比「样式丢失」更值得注意。

实验状态下抓取文章页，加载的区块样式只有：

```
wp-includes/css/dist/block-library/common.min.css
```

而该页面正文实际使用了：

| 区块类型 | 出现次数 |
| --- | --- |
| `wp-block-quote` | **11** |
| `wp-block-heading` | 7 |
| `wp-block-button` | 3 |
| `wp-block-list` | 2 |
| `wp-block-paragraph` | 2 |

对应的 `quote.min.css` / `list.min.css` / `button.min.css` … **一个都没有加载**。

**原因**：WordPress 的区块样式按需加载依赖渲染过程中能识别出区块类型
（需要在 `do_blocks()` 渲染时通过 `render_block` 钩子收集）。
Sakurairo 的内容输出方式让这个识别失效，最终只加载了全局的 `common.min.css`。

**所以「恢复按需加载」在这里并不等于「智能地只加载用到的样式」，而是「几乎一个都不加载」。**

对照现状（改动前）：主题强制 enqueue 的 `wp-block-library` 是**全量合并文件**，
包含所有区块的样式，所以正文渲染正常。

## 五、结论与选项

**T2 是真实的视觉变更，不属于「外观零变更」的范围。** 实验已回退，代码保持原状。

变化幅度总结：

| 维度 | 幅度 |
| --- | --- |
| 受影响页面 | 仅文章页 / 代码长文页（8/28）；首页、列表、独立页、404 全部零影响 |
| 主要表现 | 正文区域整体上移：桌面 12px、移动 24px（约半行到一行文字） |
| 可见的样式丢失 | **引用块左侧竖线边框消失** |
| 深度依赖区块元素的页面 | 代码长文页出现更多样式差异 |

要拿到这 137.5 KB，需要二选一：

- **方案 A：接受外观变化** —— 把它归入后续「允许视觉变更」的阶段，同时补上引用块等关键区块的样式。
  工作量可控，但需要你确认「外观不变」这个约束是否可以在此项上放宽。
- **方案 B：修好按需加载** —— 让主题的内容渲染能被 WordPress 识别，
  使按需加载真正生效。这样体积最优（只加载用到的区块样式），外观也一致。
  风险是改动了内容渲染链路，属于结构级改动，需要完整回归。

**方案 B 明显更优**，但它是结构改动，不属于零风险批次。在你有明确结论前，此项不做。

## 附：本次新增的分析工具

| 工具 | 用途 |
| --- | --- |
| `anal-size.js` | 两组截图尺寸不同时，量化共同区域内的差异像素与纵向分布 |
| `align.js` | 逐行垂直对齐检测：判断差异是「整体位移」还是「真实重排」 |
| `shiftcmp.js` | 位移补偿后逐像素对比：给出「补偿前 / 补偿后」差异率与残余分布 |

这三个工具把「页面高度变了」这种模糊结论，变成了可判断的数据 —— 建议在后续任何
涉及布局的改动中复用。
