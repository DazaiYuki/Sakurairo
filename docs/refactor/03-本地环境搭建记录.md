> 搭建日期：2026-09-24
> 位置：`D:\Sakurairo-AI\env`（**不在主题仓库内**，整目录可删）

## 一、为什么这么搭

| 需求 | 方案 | 理由 |
| --- | --- | --- |
| 不污染 C 盘 | 全部放在工作区 | 删 `env\` 即彻底卸载 |
| 免装数据库服务 | SQLite | 不用装 MySQL、不用起服务、不用配账号 |
| 免装 Web 服务器 | PHP 内置服务器 + 路由脚本 | 不用装 Apache/Nginx/IIS；静态文件由内置服务器直达，不经 PHP |
| 改代码即时生效 | 目录联接（junction） | 不用同步，主题仓库是唯一真实源 |
| 能测最新 WP | WordPress 7.1.2 | 与线上 3.0.10 主题所处的 6.x 环境形成对照 |

## 四、关键配置说明

### 4.1 wp-config.php 要点

```php
/* 数据文件限定在工作区内 */
define( 'DB_DIR',  'D:/Sakurairo-AI/env/wp/wp-content/database/' );
define( 'DB_FILE', 'sakurairo.sqlite' );

/* 固定本地地址，避免域名漂移 */
define( 'WP_HOME',    'http://localhost:8080' );
define( 'WP_SITEURL', 'http://localhost:8080' );

/* 调试：写日志不显示，避免 Notice 刷屏 */
define( 'WP_DEBUG',         true );
define( 'WP_DEBUG_LOG',     'D:/Sakurairo-AI/env/wp-content-debug.log' );
define( 'WP_DEBUG_DISPLAY', false );
```

> `WP_DEBUG_DISPLAY` 设 false 后 Notice 仍会出现，因为**主题自己 `ini_set('display_errors','1')`** 覆盖了它。这是主题缺陷（见 §6），为降噪已把 `iro_options.php_noise_filter` 设为 `inner`。

### 4.2 php.ini 要点

- `extension_dir = "ext"`，启用上表全部扩展
- `session.save_path` / `upload_tmp_dir` / `sys_temp_dir` **全部指向工作区**，避免 PHP 把临时文件写到 C 盘
- `error_log` 指向 `D:/Sakurairo-AI/env/php-error.log`
- `zend_extension=opcache`（注意不是 `extension=`，写错会报 Zend Extension 警告）

### 4.3 router.php 的作用

PHP 内置服务器默认不支持 URL 重写。路由脚本做三件事：

1. 真实存在的文件（含 .php）→ `return false`，交回内置服务器
2. 目录且有 `index.php`（如 `/wp-admin/`）→ 设置 `SCRIPT_NAME`/`SCRIPT_FILENAME` 后 require
3. 其余 → 交给 WordPress 的 `index.php` 走 rewrite

## 五、踩过的坑

| 现象 | 根因 | 解决 |
| --- | --- | --- |
| `curl http://localhost:8080` 返回 502 | 本机 `http_proxy=127.0.0.1:62062`，localhost 也被代理走 | 加 `--noproxy '*'` |
| `mklink /J` 报「参数格式不正确 - "D:"」 | Git Bash 的 MSYS 路径转换改写了参数 | 改用 PowerShell `New-Item -ItemType Junction` |
| 固定链接被写成 `/C:/Users/.../PortableGit/.../%postname%/` | 同上，MSYS 把 `/%postname%/` 当 Unix 路径改写 | `export MSYS_NO_PATHCONV=1` 后重设 |
| `php -r` 报 "Invalid library (appears to be a Zend Extension...)" | opcache 必须用 `zend_extension` 加载 | 改 php.ini |
| 每次 WP-CLI 输出夹带 4 条 Notice | 主题在错误钩子 enqueue 样式 | 见 §6，属主题待修项 |
| 后台进程随工具调用结束被回收 | 前台 shell 生命周期 | 用后台任务方式启动 |

## 六、环境自动暴露的主题问题（实测证据）

搭起来立刻就有收获 —— WordPress 自己的检查机制报出了主题问题。

### 6.1 钩子用法错误（WP 官方 "doing it wrong"）

```
Function wp_enqueue_style was called incorrectly.
Scripts and styles should not be registered or enqueued until the
wp_enqueue_scripts, admin_enqueue_scripts, or login_enqueue_scripts hooks.
This message was added in version 3.3.0.

Triggered by handles:
  - wp-block-library
  - wp-block-library-theme
  - wp-block-library-comments
  - wp-block-library-widgets
```

对应位置：`functions.php:611-624`

```php
add_action("after_setup_theme", function(){
    if(iro_opt("poi_pjax",true)==true){
        add_filter( 'wp_should_load_separate_core_block_assets', '__return_false' );
        ...
        wp_enqueue_style( 'wp-block-library' );        // ← 钩子用错了
        wp_enqueue_style( 'wp-block-library-theme' );
        wp_enqueue_style( 'wp-block-library-comments' );
        wp_enqueue_style( 'wp-block-library-widgets' );
    }
});
```

**双重问题**：
1. 在 `after_setup_theme` 里 enqueue —— 应为 `wp_enqueue_scripts`
2. 顺带关掉了区块资源按需加载 —— 这正是文档 02 里 **T2** 的成因

### 6.2 主题强行覆盖 PHP 错误显示

`functions.php` 中：

```php
if (iro_opt('php_notice_filter') != 'inner') {
    if (iro_opt('php_notice_filter','normal') == 'normal') {
        error_reporting(E_ALL & ~E_DEPRECATED);
        ini_set('display_errors', '1');    // ← 覆盖 WordPress 设置
    }
    ...
}
```

主题不该管理全局 PHP 错误配置（原审计 **S1**）。这也是本环境 Notice 压不下去的原因。

### 6.3 在模板文件里发 HTTP 头（新发现，此前未识别）

`header.php:44`

```php
$core_lib_basepath = iro_opt('core_library_basepath') ? ... ;
$nav_text_logo = iro_opt('nav_text_logo');
$vision_resource_basepath = iro_opt('vision_resource_basepath');
header('X-Frame-Options: SAMEORIGIN');   // ← 模板文件里发响应头
?>
<!DOCTYPE html>
```

**日志实证：**

```
PHP Warning: Cannot modify header information - headers already sent
by (output started at wp-includes/functions.php:6260)
in D:\Sakurairo-AI\Sakurairo\header.php on line 44
```

**因果链：**

1. `functions.php:611-624` 在错误钩子 enqueue → WordPress 输出 `_doing_it_wrong` Notice
2. 输出一旦开始，HTTP 响应头就被锁定
3. `header.php:44` 的 `header()` 调用失败

**后果**：`X-Frame-Options: SAMEORIGIN` 是防点击劫持的响应头。它一旦发不出去就**静默失效**——不会报错给用户，只是防护没了。

**为什么线上没暴露**：生产环境 `WP_DEBUG` 关闭，Notice 不打印，于是这条 `header()` 侥幸成功。但只要有任何插件提前输出、或者文件带 BOM / 结尾多余空行，防护就会失效。这是个**依赖巧合才能工作**的写法。

正确做法：移到 `template_redirect` 或 `send_headers` 钩子。

### 6.4 硬编码在模板里的资源引用

`header.php:66-70`、`77-78` 把 preconnect / preload / FontAwesome / Google Fonts 直接写死在模板里，且**位于 `wp_head()`（第 74 行）之前**。

影响：
- 这些资源无法被插件接管（缓存插件、资源优化插件都够不着）
- 无法统一加 `defer` / `async` / `media` 切换
- 与文档 02 的 **X2 / X3 / T8** 直接相关
