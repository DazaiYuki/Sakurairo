# 02 · 性能实测与优化清单

> ⚠️ **方法学提醒（2026-09-24 补记）**
>
> 本文的统计方式是「抓 HTML → 提取其中的资源 URL → 逐个 curl 测体积」。
> 这有个盲区：**凡是「由 CSS 引用的资源」都不在 HTML 里，会被漏掉** ——
> 典型代表就是 webfont 的字体文件（字体 URL 写在 `@font-face` 的 `src` 中，
> 浏览器解析 CSS 后才按需下载）。
>
> 后果：本文记的「FontAwesome 20.5 KB」只是那个 CSS，而三套字体文件实际是 **295 KB**；
> 加上 Google Fonts 的中文分片，**字体总计约 863 KB，占页面总传输的 44%**。
> 实际总额因此远高于本文的估算。
>
> 正确的测量方式与完整数据见 **[10-字体资源实测.md](10-字体资源实测.md)**，
> 工具为 `env/tools/net-measure.js`（真实浏览器加载并记录全部请求）。
> **本文其余涉及体积的数字，都建议按同样方式复核一次。**

> 实测对象：`https://www.yukicat.net/`（首页）

## 一、实测结果

### 1.1 服务器响应

| 指标 | 实测值 | PageSpeed 合格线 | 判定 |
| --- | --- | --- | --- |
| **TTFB** | **1.93 s** | < 0.6 s（绿） | ❌ 严重超标，约 3 倍 |
| HTML 传输 | 15.7 KB（原始 67.7 KB） | — | 正常 |
| 外部资源数 | 18 个 | < 50 | 正常 |

**TTFB 1.93 秒是当前最大的单点问题。** 它直接决定 FCP/LCP 的下限——无论前端怎么优化，首个像素都要等近 2 秒。这一项与主题代码无关，属于服务器/主机/插件执行耗时。

## 二、诊断：分数低在哪

把上面数据按"责任归属"重新排一遍，结论会比较反直觉：

```
首屏 436 KB
├─ 第三方             249.9 KB  ████████████████████████ 57%   ← 最大头
│   ├─ Google Analytics       164.8 KB
│   ├─ Google Fonts (CJK)      61.1 KB
│   └─ FontAwesome 整包        20.5 KB
├─ 主题 Sakurairo      78.3 KB  ████████ 18%
├─ jQuery + migrate    34.7 KB  ███ 8%        ← 插件引入，非主题
├─ 插件合并 CSS        19.9 KB  ██ 5%
└─ 其它插件            11.8 KB  █ 3%

另有：TTFB 1.93 s ← 与主题无关，但影响最大
```

**结论：主题只占首屏传输的 18%。**

所以"换了主题/重构主题 PageSpeed 就能上去"这个预期需要修正——**光重构主题，天花板有限**。真正吃掉分数的是：

1. **TTFB 1.93 s**（服务器/插件执行）→ 直接压制 FCP/LCP
2. **Google Analytics 164.8 KB**、**Google Fonts 61.1 KB**、**jQuery 34.7 KB** 三个第三方/插件项合计 **260 KB，占 60%**
3. **5 个阻塞样式表 + 2 个阻塞同步脚本** 全部在 `<head>`
4. 主题的 `* { transition: all }` 让**每个元素**参与过渡——不占传输，但持续消耗主线程与合成层

## 三、优化清单（按归属分层）

### 3.1 主题侧可改的（本项目职责内）

| # | 问题 | 证据 | 预期收益 | 风险 |
| --- | --- | --- | --- | --- |
| T1 | **主题 CSS 走 PHP 运行时拼接/压缩** | `css/index.php` 用 `preg_replace` 实时处理 ~232 KB CSS；URL 带查询串 | ⚠️ **收益已更正，见 §4.1** —— 本地实测 PHP 生成仅 7~28ms，与静态文件差距 5~20ms，**不是 TTFB 问题** | 中（需处理选项变更后的缓存失效） |
| T2 | **强制全量加载区块库样式** | `functions.php` 关掉 WP 按需加载并强制 enqueue 4 个区块样式表；线上合并包内含 **1851 条 `wp-block-*` 规则** | ✅ 已实测：体积省 137.5 KB / 减少 38% ❌ **但会造成视觉变更，见 §4.2** | 中（需回归验证内容渲染） |
| T3 | **`* { transition: all 0.4s }`** | `style.css:22`，全文档每个元素参与过渡 | 消除大规模重绘/重排，改善滚动流畅度与 TBT | 低（改为具体属性） |
| T4 | **遗留 `polyfill.js`** | 10.6 KB 传输 / 30.9 KB 解压，core-js 产物 | 现代浏览器下可直接去掉 | 低（需确认支持目标） |
| T5 | **preload 写了却白做** | `functions.php:524-527` 同时输出 `preload as=style` **和**普通 stylesheet 链接，后者照样阻塞 | 二选一，避免重复声明 | 低 |
| T6 | 内联 CSS 19.8 KB / JS 5.7 KB | 首页实测 | 外链化后可缓存 | 低 |
| T7 | `js/*.map` 8.6 MB 进仓库 | 仓库实测 | 仓库体积、克隆速度（不影响线上） | 低 |

| # | 问题 | 归属 | 预期收益 |
| --- | --- | --- | --- |
| X1 | **TTFB 1.93 s** | 主机/对象缓存/插件执行 | 最大单项收益，优先排查对象缓存与页面缓存是否生效 |

## 四、优化优先级建议

按"收益 ÷ 风险"排序，建议的顺序是：

**第一批（收益大、风险低、可立即验证）**
1. X1 排查 TTFB —— 不动代码，先确认缓存是否真的生效（收益最大）
2. T5 preload 冗余声明修正
3. T3 收敛全局 transition
4. T7 仓库 source map 清理

**第二批（需回归验证）**
5. T2 恢复区块样式按需加载 ← **主题侧最大的单项体积收益**（区块样式库 140 KB 原始 / 每页强制全量加载）
6. T4 移除 polyfill
7. T1 主题 CSS 静态化 ← 收益已下调，见 §4.1

**第三批（跨边界，需你定范围）**
8. X2 / X3 / X4 第三方与插件侧

### 4.1 ⚠️ 更正：T1「主题 CSS 静态化」的收益被高估了

本文档早先把 `css/?...` 的 **2.30 s** 记为 PHP 运行时拼接压缩的耗时，
并据此把 T1 列为"主题侧最大的单项性能问题"。**这个归因是错的。**

本地实测（绕过代理，同一环境）：

| 资源 | 第1次 | 第2次 | 第3次 | 第4次 | 第5次 |
| --- | --- | --- | --- | --- | --- |
| 主题 CSS（PHP 运行时生成并压缩） | 21 ms | 7 ms | 28 ms | 26 ms | 8 ms |
| 静态 CSS（WP 核心 block-library） | 3 ms | 3 ms | 27 ms | 2 ms | 2 ms |

**PHP 拼接 + 正则压缩的全部成本只有 5~20 ms**，属于噪声级，不是 TTFB 问题。

那线上那 2.30 s 是什么？同一批实测里，同服务器的 `app.js` 只用 0.11 s、
FontAwesome 只用 0.10 s，唯独这个带查询串的 PHP 端点慢了 20 倍。
差距无法用"正则压缩耗时"解释，**更可能出在主机侧** ——
例如边缘/CDN 对带查询串的 URL 不做缓存、或每次请求都走 PHP-FPM 冷启动。
这一点在本地环境无法复现，需要在你的主机上查（属于 X1 的范畴）。

**修正后的 T1 收益定位：**

| 收益点 | 实际价值 |
| --- | --- |
| 省掉 PHP 生成开销 | ❌ 只有 5~20 ms，可忽略 |
| 可上 CDN、可设 `immutable` 长缓存 | ✅ 真实但有条件（当前已有 `Cache-Control: max-age=86400`） |
| 规避"带查询串 URL 不被边缘缓存" | ⚠️ 待主机侧确认后才成立 |

**结论：T1 从"最大收益"下调为"待确认收益"，优先级排在 T2 之后。**

### 4.2 ✅❌ 实测：T2「恢复区块样式按需加载」—— 省 137.5 KB，但**属于视觉变更**

对 T2 做了完整实验（临时移除强制加载与关闭按需加载的 filter，采集对照后回退）。

**体积收益（首页，本地实测）：**

| | 样式表数 | 传输 | 原始 |
| --- | --- | --- | --- |
| 改动前 | 4 | 310.1 K | 362.1 K |
| 改动后 | 3 | 172.6 K | 224.6 K |
| **节省** | −1 | **−137.5 K** | **−137.5 K（−38%）** |

省掉的正是整个区块样式库 `wp-includes/css/dist/block-library/style.min.css`。

> 注：本地 PHP 内置服务器**不做 gzip 压缩**（传输量 = 原始量），
> 所以这里的"传输"数字偏高。生产环境经 gzip 后约省 20~25 KB。原始体积的对比仍然有效。

**视觉影响（视觉回归 + 位移补偿分析）：**

28 张里 8 张有变化，全部是文章页与代码长文页；首页、独立页、搜索页、404、无结果搜索页**零像素差异**。

| 截图 | 高度变化 | 直接对比 | 位移补偿后 | 性质 |
| --- | --- | --- | --- | --- |
| 文章页 · 桌面 | −12px | 1.397% | 0.245% | 82% 是整体位移 |
| 文章页 · 移动 | −24px | 3.829% | 0.965% | 同上，窄屏放大 |
| 代码长文页 · 桌面 | +2px | 1.118% | 0.655% | 位移不是主因 |

位移补偿后收敛出的**唯一实质样式变化**是：**引用块（`wp-block-quote`）左侧竖线边框消失**。

**根因比预期严重**：按需加载在 Sakurairo 上**几乎失效** —— 实验状态下文章页只加载了
`block-library/common.min.css`，而正文里 11 处 `wp-block-quote` 对应的样式**一个都没加载**。
原因是主题的内容输出方式让 WordPress 识别不出区块类型。
也就是说，「恢复按需加载」在这里 ≠「智能加载用到的样式」，而是「几乎一个都不加载」。

**结论：T2 是真实的视觉变更，不属于本轮「外观零变更」的范围。**

完整量化数据、根因分析与两个可选方案见 **[07-T2视觉影响评估.md](07-T2视觉影响评估.md)**。

**在你有明确结论前，此项不做。** 实验已回退，代码保持原状。

## 五、给主题重构目标的修正建议

原目标写的是"高性能主题"。基于实测，建议把目标拆成两条，避免把不属于主题的问题算到重构头上：

- **主题侧目标**：让主题贡献的首屏体积从 **78.3 KB → 40 KB 以内**，消除 T1–T8 全部问题
- **站点侧目标（需你决定是否纳入）**：TTFB 降到 0.6 s 内、第三方脚本 260 KB → 100 KB 以内

只做主题侧，PageSpeed 会有改善但**不会质变**；两个都做才有质变。
