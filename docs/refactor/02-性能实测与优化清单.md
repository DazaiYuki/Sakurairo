# 02 · 性能实测与优化清单

> 实测日期：2026-09-24
> 实测对象：`https://www.yukicat.net/`（首页）
> 主题版本（线上）：**3.0.10**　仓库版本：3.0.11
> 方法：curl 直连模拟移动端 UA，实测 TTFB / HTML / 逐个外部资源的传输体积
> 说明：Google PageSpeed API 当日公开配额已用尽，故改用直连实测。数据均为真实抓取，非估算。

## 一、实测结果

### 1.1 服务器响应

| 指标 | 实测值 | PageSpeed 合格线 | 判定 |
| --- | --- | --- | --- |
| **TTFB** | **1.93 s** | < 0.6 s（绿） | ❌ 严重超标，约 3 倍 |
| HTML 传输 | 15.7 KB（原始 67.7 KB） | — | 正常 |
| 外部资源数 | 18 个 | < 50 | 正常 |

**TTFB 1.93 秒是当前最大的单点问题。** 它直接决定 FCP/LCP 的下限——无论前端怎么优化，首个像素都要等近 2 秒。这一项与主题代码无关，属于服务器/主机/插件执行耗时。

## 二、诊断：分数低在哪

把上面数据按"责任归属"重新排一遍，结论会比较反直觉：

```
首屏 436 KB
├─ 第三方             249.9 KB  ████████████████████████ 57%   ← 最大头
│   ├─ Google Analytics       164.8 KB
│   ├─ Google Fonts (CJK)      61.1 KB
│   └─ FontAwesome 整包        20.5 KB
├─ 主题 Sakurairo      78.3 KB  ████████ 18%
├─ jQuery + migrate    34.7 KB  ███ 8%        ← 插件引入，非主题
├─ 插件合并 CSS        19.9 KB  ██ 5%
└─ 其它插件            11.8 KB  █ 3%

另有：TTFB 1.93 s ← 与主题无关，但影响最大
```

**结论：主题只占首屏传输的 18%。**

所以"换了主题/重构主题 PageSpeed 就能上去"这个预期需要修正——**光重构主题，天花板有限**。真正吃掉分数的是：

1. **TTFB 1.93 s**（服务器/插件执行）→ 直接压制 FCP/LCP
2. **Google Analytics 164.8 KB**、**Google Fonts 61.1 KB**、**jQuery 34.7 KB** 三个第三方/插件项合计 **260 KB，占 60%**
3. **5 个阻塞样式表 + 2 个阻塞同步脚本** 全部在 `<head>`
4. 主题的 `* { transition: all }` 让**每个元素**参与过渡——不占传输，但持续消耗主线程与合成层

## 三、优化清单（按归属分层）

### 3.1 主题侧可改的（本项目职责内）

| # | 问题 | 证据 | 预期收益 | 风险 |
| --- | --- | --- | --- | --- |
| T1 | **主题 CSS 走 PHP 运行时拼接/压缩** | `css/index.php` 用 `preg_replace` 实时处理 ~232 KB CSS；URL 带查询串，响应实测 **2.30 s** | 改静态文件 + 版本号 → 可上 CDN、可长缓存、TTFB 直降 | 中（需处理选项变更后的缓存失效） |
| T2 | **强制全量加载区块库样式** | `functions.php:611-624` 关掉 WP 按需加载，并强制 enqueue 4 个区块样式表；线上合并包内含 **1851 条 `wp-block-*` 规则** | 恢复按需加载，可去掉大量无用区块 CSS | 中（需回归验证编辑器内容显示） |
| T3 | **`* { transition: all 0.4s }`** | `style.css:22`，全文档每个元素参与过渡 | 消除大规模重绘/重排，改善滚动流畅度与 TBT | 低（改为具体属性） |
| T4 | **遗留 `polyfill.js`** | 10.6 KB 传输 / 30.9 KB 解压，core-js 产物 | 现代浏览器下可直接去掉 | 低（需确认支持目标） |
| T5 | **preload 写了却白做** | `functions.php:524-527` 同时输出 `preload as=style` **和**普通 stylesheet 链接，后者照样阻塞 | 二选一，避免重复声明 | 低 |
| T6 | 内联 CSS 19.8 KB / JS 5.7 KB | 首页实测 | 外链化后可缓存 | 低 |
| T7 | `js/*.map` 8.6 MB 进仓库 | 仓库实测 | 仓库体积、克隆速度（不影响线上） | 低 |
| T8 | FontAwesome 整包加载 | `header.php:69-70`，整包 all.min.css | 换按需图标子集，可省大半 | 中（图标兼容） |

### 3.2 非主题侧（需要你确认是否纳入范围）

| # | 问题 | 归属 | 预期收益 |
| --- | --- | --- | --- |
| X1 | **TTFB 1.93 s** | 主机/对象缓存/插件执行 | 最大单项收益，优先排查对象缓存与页面缓存是否生效 |
| X2 | Google Analytics 164.8 KB 同步在 body | 第三方 | 改 `defer`/延迟加载，或改服务端埋点 |
| X3 | Google Fonts CJK 61.1 KB CSS | 第三方 | 改自托管子集化字体，或 `font-display` + 本地化 |
| X4 | jQuery + jQuery Migrate 34.7 KB，**head 内同步** | 插件（zotpress / yukicatslider 之一） | 确认哪个插件依赖，评估去 jQuery 化 |
| X5 | FontAwesome 20.5 KB | 主题（可改）见 T8 | — |

> **关于 jQuery 的更正**：上一版审计把 jQuery 记为"主题前端依赖（22 处 PHP）"，**这是错的**。经逐文件核对：主题 PHP 前台**没有** `wp_enqueue_script('jquery')`；主题 JS 中只有 `page.js` 出现 2 次 `jQuery` 字样，`nav.js` / `app.js` / `smoothscroll.js` / `polyfill.js` 均为 **0**。线上那两个 jQuery 文件是**插件**引入的。误记已在此更正。

## 四、优化优先级建议

按"收益 ÷ 风险"排序，建议的顺序是：

**第一批（收益大、风险低、可立即验证）**
1. X1 排查 TTFB —— 不动代码，先确认缓存是否真的生效（收益最大）
2. T5 preload 冗余声明修正
3. T3 收敛全局 transition
4. T7 仓库 source map 清理

**第二批（需回归验证）**
5. T2 恢复区块样式按需加载
6. T4 移除 polyfill
7. T1 主题 CSS 静态化 ← **收益最大，但要设计缓存失效**

**第三批（跨边界，需你定范围）**
8. X2 / X3 / X4 第三方与插件侧

## 五、给主题重构目标的修正建议

原目标写的是"高性能主题"。基于实测，建议把目标拆成两条，避免把不属于主题的问题算到重构头上：

- **主题侧目标**：让主题贡献的首屏体积从 **78.3 KB → 40 KB 以内**，消除 T1–T8 全部问题
- **站点侧目标（需你决定是否纳入）**：TTFB 降到 0.6 s 内、第三方脚本 260 KB → 100 KB 以内

只做主题侧，PageSpeed 会有改善但**不会质变**；两个都做才有质变。
