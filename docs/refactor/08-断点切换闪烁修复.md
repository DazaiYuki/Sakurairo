# 08 · 断点切换闪烁修复

> 修复日期：2026-09-24
> 现象来源：用户报告 ——「调整浏览器窗口大小时，在桌面/平板/手机的适配尺寸切换节点会突然样式异常，闪一下又恢复」
> 结论：**根因是 `transition: all` 把断点切换时的布局变化做成了动画**；已修复，实测错乱期 928ms → 0~33ms

---

## 一、现象与定位思路

用户描述的特征是「**突然异常 → 闪一下 → 恢复**」。这个时间形态本身就指向 CSS 过渡：
布局变化在一瞬间定了，但被过渡拉长成一段动画，中间态看起来就是"错乱"。

诊断方法是直接量化：注入 rAF 采样循环，逐帧记录约 200 个元素的
`getBoundingClientRect()`，统计「每帧有多少元素的几何信息与上一帧不同」。

- 页面静止时，这个数字应该接近 0
- 切换断点后，如果这个数字**连续多帧保持在很高水平**，说明布局变化正在被动画化

工具：`env/tools/flash-detect.js`

---

## 二、根因

### 2.1 实测数据

```
切换前基线：单帧最多 7 个元素在变化
切换后  ：峰值 205 / 205 个元素同时变化，持续 928ms
```

**切换断点后，页面上每一个元素都开始做过渡动画，持续约 0.9 秒。**

### 2.2 来源：不是一条规则，而是 75 条

最初的判断是 `style.css` 顶部那条：

```css
* {
  transition: all 0.4s cubic-bezier(0.07, 0.53, 0.65, 0.95);
}
```

但把它收窄为「不触发重排的属性」后，实测**毫无改善（仍 928ms）**。
原因：主题内还有 **74 条组件级 `transition: all`**，优先级高于通配符，把收窄覆盖了。

| 文件 | 条数 |
| --- | --- |
| `style.css` | 55 |
| `css/responsive.css` | 8 |
| `css/sakura_header.css` | 6 |
| `css/dark.css` | 5 |

其中包含 `nav ul li { transition: all 1s ease }` 这类高频元素，这是错乱期长达 0.9 秒的原因。

### 2.3 中途一次失败的尝试（值得记录）

第二步尝试：**只在 resize 期间收窄到「不触发重排的属性」**，白名单包含
color / background / box-shadow / opacity / **transform** / filter 等。

实测仍有 422ms。用 `probe-resize.js` 逐帧探测后定位到：

```
nav ul li          top: 19 → -15      （断点切换后）
.nav-article-title top: 59 → 23
```

**导航栏的位置调整是靠 `transform` 完成的** —— 而 transform 在白名单里，
所以它仍在做 0.4 秒动画。只排除"布局属性"是不够的。

---

## 三、修复方案

### 3.1 为什么不全局改写那 74 条

全局把 `transition: all` 收窄，会连带影响**依赖布局属性做动效的组件**：

| 组件 | 依赖的属性 |
| --- | --- |
| `.mobile-nav` / `.mo_toc_panel`（移动端抽屉） | `max-height: 0 → 100vh` |
| `.mobile-nav .sub-menu` | `max-height: 0 → 50vh` |
| `.top-social .inner` / `.slider li .inner` | `max-height: 0 → 121px` |
| `.medal-progress-bar` | `width` |
| `#baguetteBox-slider` | `left` |
| `nav ul li a:after` | `max-width` |

这些改完会从"平滑展开"变成"瞬间展开"，属于动效降级 —— 为避免它，
不在静态规则上做全局改写。

### 3.2 实际方案：只在窗口尺寸变化期间禁用过渡

```css
html.iro-resizing * {
  transition: none !important;
}
```

```js
// functions.php → wp_footer
function mark() {
    root.classList.add('iro-resizing');
    clearTimeout(timer);
    timer = setTimeout(function () {
        root.classList.remove('iro-resizing');
    }, 1200);
}
window.addEventListener('resize', mark, { passive: true });
window.addEventListener('orientationchange', mark, { passive: true });
```

三个要点：

1. **只在 resize 期间生效**，日常动效（含移动端抽屉、折叠面板）一个都不改
2. **全部禁用而非只排除布局属性** —— 因为导航用 transform 定位（见 §2.3）
3. **保持 1.2 秒**，覆盖主题最长的 1s 过渡（`nav ul li`、`.site-footer`），留 200ms 余量

> 曾尝试「检测页面尺寸稳定后提前撤下」，但失败了：header 高度固定，
> 导航内部的布局变化不影响整页高度，会被误判为已稳定。
> 固定时长更可靠。

## 四、验证结果

### 4.1 闪烁（`flash-detect.js`，7 组视口切换）

| 页面 | 切换 | 修复前 | 修复后 |
| --- | --- | --- | --- |
| 文章页 | 1200→880 | 422 ms | **33 ms** |
| 文章页 | 1100→870 | 441 ms | **12 ms** |
| 文章页 | 1440→800 | 928 ms | **0 ms** |
| 首页 | 1440→390 | 932 ms | **0 ms** |
| 首页 | 1000→850 | — | **0 ms** |
| 首页 | 1440→1080 | — | **20 ms** |
| 代码长文页 | 1440→820 | — | **0 ms** |

残留的 12~33ms 约等于 1~2 帧，人眼不可见（原 928ms 约 55 帧）。

### 4.2 静态渲染（视觉回归）

28 张全页截图与基准逐像素对比：**28/28 完全一致**（退出码 0）。

采集过程中另外发现并修复了一个**工具层面**的问题：截图脚本原先只靠 cookie 指定配色，
而主题的深色模式默认是「自动切换」（策略 `time`，22:00~7:00 转暗色），
白天采集时前端 JS 会把 cookie 带来的 `dark` class 移除，导致 16 张暗色截图渲染成亮色。
现已改为在 `addInitScript` 中写 `localStorage.dark` —— 与前台手动切换是同一机制。
详见 `env/tools/README.md`。

> 此前所有采集都在凌晨进行，恰好落在自动暗色时段，问题一直没暴露。

### 4.3 日常动效

未改动任何组件级过渡规则，hover、抽屉展开、折叠面板动效均保持原样。

## 五、遗留项

**74 条组件级 `transition: all` 仍在**。它们带来的是"意外动画化"的风险
（例如 resize、字体加载完成、脚本改样式时的不必要动画），属于性能债。

收窄它们能进一步提升性能，但需要逐个判断哪些组件依赖布局属性做动效（§3.1 的表是初步清单，可能有遗漏）。
在拿到完整的依赖清单前不动 —— 这与 T2 的处理原则一致：
**不做没有验证手段的改动。**
