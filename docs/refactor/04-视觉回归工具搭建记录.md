# 04 · 视觉回归工具搭建记录

> 搭建日期：2026-09-24
> 位置：`D:\Sakurairo-AI\env\tools`（**不在主题仓库内**）
> 目的：为"外观零变更"提供可执行的验证手段，而不是靠人眼

---

## 一、为什么必须做

重构 Sakurairo 的硬指标是「保持外观设计不变」。但主题有 499 个 PHP 文件、43 个 CSS 文件，
靠人眼逐页检查不现实，也没法在每次改动后重复执行。

视觉回归提供的是**可重复的机器判定**：

```
改代码前  → 采集基准
改代码后  → 采集对照
          → 逐像素对比
          → 一致 = 外观没变；有差异 = 定位到具体页面/位置
```

---

## 二、技术选型

| 项 | 选择 | 理由 |
| --- | --- | --- |
| 浏览器 | Playwright + Chromium | 截图 API 稳定，支持 `mask` 遮罩与请求拦截 |

| npm 缓存 | `env/tools/.npm-cache` | 同上，不写 C 盘 |
| 图像对比 | pixelmatch + pngjs | 纯 JS，无需编译 |
| 需要额外装的 | 无 | 数据库/服务器复用已有的本地环境 |

## 四、确定性：整个过程最难的部分

第一版跑完，同一份代码连续采集两次，24 张里只有 **10 张**一致。
说明当时根本无法区分「重构造成的真实变化」和「渲染抖动」。

于是逐条排查抖动来源，逐个消除：

| # | 抖动来源 | 原因 | 处理方式 |
| --- | --- | --- | --- |
| 1 | 文章/评论的相对时间 | `poi_time_since()` 显示 "X minutes ago" | 内容回填到 30 天前（该函数超过 30 天阈值改用绝对日期） |
| 2 | 评论时间 | 同上 | 改 `wp_comments.comment_date` |
| 3 | 浏览次数 | `set_post_views()` 挂 `get_header`，无去重自增 | mu-plugin 移除钩子 + 固定计数 |
| 4 | 上下篇缩略图 | 外部随机图 API | 路由拦截替换为固定图 |
| 5 | **卡片主题色** | 颜色由封面图**服务端实时提取**，默认封面走随机图 API | 设置真实的**本地**特色图 |
| 6 | 外部字体/CDN | 加载失败回退字体 → 行高变化 → 整页位移 1~2px | 外部资源缓存到 `env/cache/http/` |
| 7 | **懒加载封面** | 滚动触发有竞态，截图时图片可能未加载完 | 强制写回 `data-src` + 等所有图片落地 |
| 8 | CSS 过渡/动画 | 元素停在过渡中间态 | 注入 `transition:none; animation:none` |

**收敛过程：**

```
仅冻结动画                    10 / 24
+ 遮罩 + 随机图桩              15 / 24
+ 外部资源缓存                19 / 24
+ 内容回填 30 天前            19 / 24   ← 此时可去掉全部遮罩
+ 修评论日期                  23 / 24
+ 本地特色图                  23 / 24
+ 强制加载图片 + 超时          24 / 24   ✓（此结论后被发现带潜在误报，见下）
```

### 4.1 ⚠️ 上面那个 24/24 曾经不可靠 —— 两处后续修正

**修正一：导航栏文章标题的显隐抖动（复现率约 60%）**

`nav.js` 用 `[data-scrollswap]` 属性 + 内联 opacity 切换导航栏的"菜单 / 文章标题"。
`fullPage: true` 截图会把视口临时撑到整页高度，这个 resize 会异步触发该切换，
时序不稳 —— 也就是说上面那轮"24/24"大约每 5 次就有 3 次会误报。

修法：截图前显式 `removeAttribute('data-scrollswap')`，并清掉 `.nav-article-title`
的内联 `opacity` / `transform`，复位到"页面顶部"应有的状态。

**修正二（根因）：prev/next 卡片的背景图懒加载没被处理**

长时间内一直存在一处"文章页 prev/next 区域随机漂移"的差异（0.02%~0.25%），
一度以为本机渲染噪声。真正原因是主题的卡片结构：

```html
<div class="background lazyload"
     style="background-image:url(占位图)"
     data-src="真实图">
```

**`data-src` 挂在 `div` 上、走背景图**，而不是 `<img>`。
截图脚本早先只处理了 `img[data-src]`，**漏掉了这种 div**，
于是背景图时有时无。

补上 `[data-src]:not(img)` 的处理后：
**4 轮 × 4 组合连续 16 次对比全部零差异。**

**同时把稳定性签名补全**，加入两个此前遗漏的维度：

| 维度 | 作用 |
| --- | --- |
| `document.body.scrollHeight` | 捕捉"位移型"差异 —— 上方元素高度变化会把下方内容整体推移，只看单个元素的计算样式发现不了 |
| 未完成图片数 | 捕捉仍在加载中的图片 |

### 4.2 当前状态

- **28 / 28 零差异，退出码 0**（回归集已从 24 张扩到 28 张，见第四节）
- 工具默认容差从 0.15% **恢复为严格 0** —— 噪声根因已消除，任何差异都应当作真实回归来查

> 教训：把"随机漂移的差异"归因为"环境噪声"是危险的。
> 那其实是工具漏处理了一种懒加载形态，属于**工具自身的 bug**，
> 却差点被当成正常现象接受。每次遇到"位置会变"的差异，都应先怀疑工具而不是环境。

## 五、踩过的坑

| 现象 | 根因 | 解决 |
| --- | --- | --- |
| `require('pixelmatch')` 报错 | pixelmatch v7 起是纯 ESM，**且 package.json 没有 exports 字段**，Node 无法自动互操作 | CommonJS 里用动态 `import()` |
| 脚本卡死 9 分钟不退出 | 等图片完成的 `Promise.all` 没有超时；个别图片既不触发 `load` 也不触发 `error` | 加 `Promise.race` 超时兜底 |
| `wp comment update --comment_date=` 无效 | `wp_update_comment()` 会忽略日期字段，**静默失败**。用 `wp comment list` 一看日期根本没变 | 改用 `$wpdb->update()` 直接写 |
| `rm -rf` 被安全策略拦截 | 批量删除超过阈值 | 不需要删，直接用同名目录覆盖 |
| `console.log('%-42s', x)` 格式无效 | Node 的 `console.log` 不支持宽度修饰符 | 自己实现 `pad()` 并按双宽计算中文 |
| `_diff` 目录混入上一轮旧图 | compare 没有清理输出目录 | 每次都先清空 `_diff/` |

## 八、工具顺带暴露的主题问题

### 8.1 浏览量自增无任何去重（性能相关）

`functions.php:815`

```php
function set_post_views() {
    ...
    update_post_meta( $post_id, 'views', ($views + 1) );
}
add_action('get_header', 'set_post_views');
```

**每次加载单页就写一次数据库**，没有 cookie 判断、没有时间窗口限制。
对比 WP-PostViews 等成熟实现，普遍会加 cookie 去重。

影响：
- 每次浏览多一次写库
- 与页面缓存天然冲突（缓存命中时不执行，计数就会丢）
- 容易被刷量

### 8.2 404 页面脱离主题体系（已在文档 03 记录）

`404.php:182` 硬编码 `<body class="page-404">`，不走 `body_class()`、不包含 `header.php`。
后果是暗色模式失效、主题 body 类全部丢失。视觉回归工具因此无法对 404 页做暗色对比（2 张暗色 404 实际是浅色）。

## 十、工具实战案例：抓住一次"无报错的静默失败"（2026-09-24）

**背景**：评估 T4 时判断 `polyfill.js` 是"core-js 死代码"（依据：内容全是 ES6 API
补丁，而 app.js 用 ES2020 语法，老浏览器根本跑不了 app.js，polyfill 无用武之地），
于是移除了它的加载。

**视觉回归立刻报警**：28 张中 24 张异常——首页高度 3282px → 2268px（−1014px），
20 张"尺寸变化"，04-page 位移 15px 造成 98% 像素差异。且 console **零报错**。

**排查链**（新增工具 `dom-heights.js` / `console-probe.js`）：

1. 重采一次 → 逐字节复现 → 排除网络偶发
2. `git stash` 后重采 → 高度恢复 3282px → 确认是代码改动引起（而非环境漂移）
3. DOM 逐区块探针 → 消失的是首页 900px 高的全屏 `CANVAS`（banner 背景）
4. 内容分析 → polyfill.js 开头是
   `(globalThis.webpackChunksakurairo_scripts ||= []).push([[8538], {...}])`

**真相**：polyfill.js 不是独立的 API 补丁，而是 **webpack chunk 8538**——
它和 app.js 同属 `webpackChunksakurairo_scripts` chunk 体系，app.js 引用其中的
core-js helper 模块。缺失时相关模块链**异步静默失败**（Promise reject 无 console
错误），canvas 初始化不执行。此前"app.js 是 ES2020 所以老浏览器跑不了"的推理
虽然正确，但结论无关紧要——**现代浏览器同样需要 chunk 8538 里的模块**。

"polyfill.js 自己也有 144 处箭头函数"这一疑点本应引起警觉：给不支持 ES6 的浏览器
打补丁的文件自己却不兼容 ES6，说明它根本不是给那些浏览器用的——当时误判为
"打包配置错误产生的废料"，实际是"webpack 产物本来如此"。

**处置**：`git checkout` 回退，首页 4 张截图恢复 0.0000% 差异。
T4 在文档 02 中标记为**不可移除**。

**两条教训**：

1. **JS 文件的"身份"不能靠内容特征推断**。构建产物（webpack/rollup 输出）的
   chunk 之间有隐式依赖，表面看是"polyfill"的文件可能是运行时核心。
   移除构建产物前，要么读源码仓库的打包配置，要么像这次一样先跑回归。
2. **静默失败只有像素对比能抓住**。console 干净、PHP 日志干净、HTTP 全 200——
   唯独页面少了一块 900px 的画布。这正是视觉回归存在的意义。
