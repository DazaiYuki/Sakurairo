### ⚠️ 关于 `Tested up to: 6.8` 的正确理解

**`Tested up to` 只是"兼容性声明"，不是"符合该版本规范"的证明。**

它的含义仅限于：作者声明在该版本上能正常运行、不会崩。它**不代表**：

- 代码写法符合该版本的官方标准
- 已接入该版本引入的新机制（区块、theme.json、编辑器 API 等）
- 没有使用已被弃用的 API
- 性能或安全性达到该版本推荐水平

所以本项目要区分两个目标：

1. **兼容层**：让声明与事实相符，不再被标记为"未测试"主题
2. **规范层**：真正按现代 WordPress 标准改造代码（这才是"符合规范"）

## 2. 技术债清单

### 2.1 架构债（最重）

| # | 问题 | 证据 | 影响 |
| --- | --- | --- | --- |
| A1 | **`functions.php` 巨石** | 4545 行 / 188 KB / 129 个函数 / 40 处 `include` | 单文件承载全部引导逻辑，无法单测，改动易误伤 |
| A2 | **两套选项框架并存** | `opt/` = Codestar Framework 2.3.0e（Fuukei 分支，~420 选项）；`inc/kirki/` = Kirki 5.1.0 | 两套数据模型、两套 UI、两套维护负担 |
| A3 | **Kirki 整包内置 3.7 MB** | `inc/kirki/`，仅服务原生 Customizer；上游 Themeum 已停更 | 背着一个弃维护库 |
| A4 | **JS 源码不在本仓库** | `js/` 全是 webpack 产物；源码在 `Fuukei/Sakurairo_Scripts`，经 CI 复制 | **重构 JS 的硬约束**，见 §3 R1 |
| A5 | **无构建系统 / 无依赖管理** | 主题根目录无 `package.json`、无 lockfile | 无法做 tree-shaking、代码分割 |
| A6 | **无 `theme.json`** | 文件不存在 | 无法接入 FSE / 全局样式 / 设计令牌 |
| A7 | **`.git` 膨胀至 133 MB** | 历史反复提交构建产物与二进制资源 | 克隆慢、diff 噪音大 |
| A8 | 第三方库直接 vendored | `inc/Parsedown.php`、`inc/classes/Meting.php`、`Aplayer.php`、`update-checker/`(PUC 453 KB) | 升级需手工，安全补丁滞后 |

| # | 问题 | 证据 |

### 2.3 规范 / 安全债

| # | 问题 | 证据 | 影响 |
| --- | --- | --- | --- |
| S1 | **主题内改 PHP 错误级别** | `functions.php` 中 `error_reporting()` + `ini_set('display_errors','1')` | 生产环境暴露错误细节；主题不该管全局 PHP 配置 |
| S2 | **33 处直接 `$wpdb` 查询** | 散布于 `inc/` 与模板 | 需逐条审查注入与索引 |

**值得肯定的部分**（说明代码基调可控）：

- `query_posts`、`create_function`、`@extract`、未转义 `echo $_GET/$_POST` 均为 **0 处**
- 已有 `Cache.php` / `Captcha.php` / `Turnstile.php` / `Vaptcha.php` 等抽象
- 主题前台**不引入 jQuery**（已逐文件核对），主题 JS 全部在 `</body>` 前，`nav.js` 带 `defer` —— 这几点做得是对的
- 近期上游提交在做安全修复（评论私密接口越权、CSS 注入过滤、输入净化）

## 3. 硬约束与风险

### 🔴 R1 — JS 源码在外部仓库

```
Fuukei/Sakurairo_Scripts (源码)  ──yarn build──►  dist/  ──CI 复制──►  Sakurairo/js/
```

主题仓库里没有 JS 源码。要重构前端，只能：fork 源码仓库 / 把源码迁入主题 / 冻结 JS。→ 决策点 D1。

### 🔴 R2 — 选项数据兼容性（改错会毁掉所有站点）

`iro_options` 单个 option 存着约 420 个配置项。重构选项框架时若 key 或数据形状变了，**用户升级后配置全部归零**。这是全项目风险最高的一步，必须最后做，且必须带迁移与回滚。

### 🟠 R3 — 视觉零变更如何验证

"外观不变"是硬指标，但没有可运行的 WordPress 环境就无法验证。→ 决策点 D2。

### 🟠 R4 — 分叉上游后的维护模式

完成 L3/L4 后与上游结构性分叉，无法再自动合并上游更新。→ 决策点 D4。

## 4. 重构分层

```
L0  地基       本地 WP 环境 · 视觉基线快照 · 回归脚本 · 静态检查
L1  低风险收益  移除 source map · 收敛全局 transition · 错误级别 · CSS 毛刺
L2  兼容升级    Tested up to · PHP 8.3 弃用清理 · $wpdb 审计 · 渲染阻塞治理
L3  结构重构    functions.php 模块化 · 选项框架收敛 · 依赖外置/升级
L4  现代化      构建链 · theme.json · 块编辑器集成
```

### 核心原则

1. **视觉零变更** —— 每步改动渲染结果必须与基线一致
2. **数据向后兼容** —— 选项 key、option 名、主题目录名、`IRO_VERSION` 语义不动
3. **增量 + 可回滚** —— 一步一个 commit，commit message 说明改了什么、为什么
4. **先测后改** —— 先建基线再动代码
5. **不做大爆炸重写**

## 6. 需要决策的点

### D1 · JS 源码策略（决定前端改造可行性）

| 选项 | 说明 | 代价 |
| --- | --- | --- |
| A. 同时 fork `Sakurairo_Scripts` | 在源码仓库现代化（去 jQuery、Vite 化），再同步产物 | 多维护一个仓库，CI 要改 |

| C. 冻结 JS，只改 PHP/CSS | 放弃前端重构 | 部分性能项无法解决 |

### D2 · 视觉回归环境
是否搭建本地 WordPress 做改前改后截图对比？不搭则"外观不变"无法验证。

### D3 · 选项框架最终形态
保留并现代化 CSF / 转向 Kirki（上游停更，**不推荐**）/ 收敛到原生 API。
无论选哪条，**Kirki 都应移除**。

### D4 · 与上游的关系
是否接受 L3 之后彻底独立维护。
